Reverseed Domain Design

스터디 파티 플랫폼 도메인 설계

GitHub 계정은 로그인과 연동에 사용하지만, 파티 안에서는 파티별 닉네임과 프로필을 중심으로 활동을 표시하는 privacy-first 스터디 플랫폼 설계 문서입니다.

기준 날짜: 2026-05-30 소스: Prisma + Server Domain 스타일: standalone HTML

1. 설계 목표

익명성

Privacy

사용자는 GitHub OAuth로 로그인하지만 파티 내부에서는 PartyProfile.nickname을 기본 표시명으로 사용합니다. GitHub 원본 링크와 계정 정보는 명시된 조건에서만 노출합니다.

스터디 단위

Party

Party는 공개/비공개, 태그, 대문 Markdown, 멤버십, 초대, 참여 신청을 소유합니다. parentId로 1-depth mini party를 표현합니다.

GitHub 활동 피드

Webhook

등록된 GitHub repository의 webhook event를 파티 활동으로 변환하고 홈 피드와 파티 피드에 반영합니다.

3. Bounded Context

Identity & Relationship

User
  • User: Auth.js 사용자, GitHub OAuth 계정의 소유자
  • Account, Session: 인증 세션
  • Friendship: 친구 관계, 양방향 승인 상태
  • CloseFriend: 단방향 친한 친구 표시

Party Collaboration

Party
  • Party: 파티와 mini party의 aggregate root
  • PartyMembership: 역할과 참여 상태
  • PartyProfile: 파티별 닉네임/아바타/상태
  • PartyJoinRequest, PartyInvite: 공개 신청과 비공개 초대
  • Tag, PartyTag: 공개 검색/추천 기준

GitHub Integration

GitHub
  • GitHubRepository: owner/name/fullName 기준 repository
  • PartyRepository: 파티와 repository 연결 및 GitHub App 설치 상태
  • GitHubWebhookEvent: delivery id 기준 원본 webhook 저장
  • GitHubDraft: issue, PR, comment, commit 작성 초안

Activity & Comment

Feed
  • PartyActivity: 파티 피드와 홈 피드에 표시되는 활동
  • PlatformComment: 플랫폼에서 작성한 댓글과 GitHub 반영 결과
  • ActivityGitHubLinkAccess: GitHub 원본 링크 노출 권한 기록

4. 핵심 엔티티 관계

관계 설명 주요 제약
User -> PartyMembership -> Party 사용자가 파티에 소속되는 관계입니다. @@unique([partyId, userId])
User -> PartyProfile -> Party 파티 안에서 보여줄 닉네임과 프로필입니다. @@unique([partyId, userId])
Party -> Party parentId로 mini party를 표현합니다. 현재 정책상 mini party는 parent party 멤버만 참여 가능
Party -> PartyRepository -> GitHubRepository 파티가 GitHub repository를 등록 요청하고 App 설치 후 활성화합니다. @@unique([partyId, repositoryId])
GitHubWebhookEvent -> PartyActivity 하나의 webhook event가 repository를 등록한 파티별 활동으로 변환됩니다. @@unique([partyId, githubWebhookEventId])
PartyActivity -> PlatformComment 플랫폼 댓글은 파티 활동에 연결되고 필요하면 GitHub에도 작성됩니다. 작성 시 파티 활성 멤버십과 GitHub App 설치 필요

5. Aggregate와 불변 조건

Party Aggregate

  • root: Party
  • 소유: membership, profile, join request, invite, tag relation
  • 비공개 party는 초대 링크나 멤버십 없이는 탐색 불가
  • mini party는 parent party 멤버만 참여 가능
  • party 생성자는 OWNER membership과 기본 profile을 동시에 생성

Repository Registration Aggregate

  • root: PartyRepository
  • 등록 요청과 GitHub App 설치 완료를 분리
  • 상태: REQUESTED -> PENDING_INSTALLATION -> ACTIVE
  • 설치 실패 시 INSTALLATION_FAILED로 전이

Activity Aggregate

  • root: PartyActivity
  • webhook delivery는 파티별로 한 번만 activity로 반영
  • 원본 GitHub URL은 policy를 통과한 사용자에게만 노출

Relationship Aggregate

  • root: Friendship, CloseFriend
  • 친구는 양방향 승인
  • 친한 친구 표시는 단방향 가능
  • A가 B를 친한 친구로 등록하면 B에게 A의 GitHub 계정 공개

6. 도메인 정책

정책 함수 입력 판단
canRevealGitHubIdentity viewer, subject, friendship, close friend 본인이거나 친구 관계에서 subject가 viewer를 close friend로 지정한 경우 공개
canRevealGitHubActivityLink activity author, GitHub actor match, repository registrant, close friend 작성자, webhook 당사자, repository 등록자, actor의 close friend에게 공개
canDiscoverParty visibility, membership, invite token PUBLIC은 탐색 가능, PRIVATE은 멤버 또는 초대 토큰 필요
canJoinMiniParty visibility, parent membership, invite token parent party 멤버가 아니면 불가. 비공개 mini party는 초대 토큰 필요
nextRepositoryRegistrationStatus currentStatus, appInstalled, installationFailed GitHub App 설치 여부에 따라 repository registration 상태 전이

7. 주요 유스케이스 흐름

파티 생성

사용자가 title, topic, capacity, visibility, tags, nickname을 입력합니다.
slugify로 고유 slug를 생성합니다.
Party, OWNER PartyMembership, PartyProfile, tags를 transaction성 create로 생성합니다.

Mini party 생성/참여

parent party가 존재하고 1-depth root party인지 확인합니다.
요청자가 parent party ACTIVE 멤버인지 검증합니다.
PUBLIC mini party는 parent 멤버가 바로 참여 가능하고 PRIVATE은 초대 토큰이 필요합니다.

Repository 등록

파티 ACTIVE 멤버가 owner/repo 또는 GitHub URL을 입력합니다.
GitHubRepository metadata를 upsert합니다.
PartyRepository를 PENDING_INSTALLATION으로 만들고 GitHub App install URL을 반환합니다.
설치 완료 시 appInstallationId를 저장하고 ACTIVE로 전환합니다.

Webhook -> Activity

GitHub signature와 delivery id를 검증합니다.
GitHubWebhookEvent를 delivery id 기준 upsert합니다.
repository에 연결된 ACTIVE PartyRepository를 조회합니다.
파티별 PartyActivity를 upsert해 홈/파티 피드에 표시합니다.

플랫폼 댓글 -> GitHub 댓글

작성자가 파티 ACTIVE 멤버인지 확인합니다.
활동이 GitHub issue/PR number와 repository를 가지고 있는지 확인합니다.
GitHub App installation이 ACTIVE인지 확인합니다.
Posted from Reverseed by [nickname](platformUrl) 서명을 붙여 GitHub App으로 댓글을 작성합니다.
PlatformComment에 platform/GitHub URL과 comment id를 저장합니다.

GitHub 링크 노출

activity author, webhook actor match, repository registrant 여부를 확인합니다.
친구 관계와 close friend 지정 방향을 확인합니다.
통과한 사용자에게만 원본 GitHub URL을 표시하고, 필요하면 ActivityGitHubLinkAccess에 근거를 저장합니다.

8. API 경계

Endpoint 역할 도메인 경계
GET /api/parties 내가 속한 party 목록 조회 Membership 기준 홈 좌측 party 목록
POST /api/parties party 또는 mini party 생성 Party aggregate 생성, mini party parent membership 검증
POST /api/parties/[partySlug]/repositories party repository 등록 요청 PartyRepository registration aggregate
POST /api/github/webhook GitHub webhook 수신 WebhookEvent 저장 후 PartyActivity 생성
POST /api/parties/[partySlug]/activities/[activityId]/comments 플랫폼 댓글 작성 및 GitHub 반영 PlatformComment + GitHub App comment
/api/github/actions Markdown 기반 issue, PR, comment, commit 작성 GitHubDraft와 GitHub REST API 경계

10. 현재 코드에서 더 분리하면 좋은 지점

Party application service

party 생성, mini party 생성, join request 승인/거절은 route handler에 로직이 남아 있습니다. 다음 단계에서는 PartyService와 PartyRepositoryPort로 분리하는 편이 좋습니다.

Link visibility materialization

ActivityGitHubLinkAccess 모델은 준비되어 있으나 모든 유스케이스에서 materialize되지는 않았습니다. webhook actor와 party member의 GitHub 계정 매칭 규칙을 별도 policy/service로 분리할 수 있습니다.

Invite lifecycle

초대 링크의 만료, 사용 횟수 증가, revoked 처리 정책을 PartyInvite aggregate policy로 명시하면 비공개 파티 접근 제어를 더 안정적으로 유지할 수 있습니다.

GitHub App installation callback

repository 등록 요청과 설치 완료는 분리되어 있습니다. 설치 callback 또는 수동 활성화 route에서 activatePartyRepository를 호출하는 흐름을 완성해야 합니다.

이 문서는 현재 구현 기준의 도메인 설계 산출물입니다. 운영 전에는 GitHub 계정 매칭, 친구/친한친구 변경 시 권한 재계산, private party URL 직접 접근 정책을 추가 테스트하는 것이 좋습니다.
